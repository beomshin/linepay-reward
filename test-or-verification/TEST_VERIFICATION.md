# 15. 테스트 및 검증

> 자동화 테스트 코드: `test-or-verification/src/test/java/com/linepay/reward/`
> QA 항목과 테스트 매핑: `test-or-verification/QA_LIST.md`
> 실행: `./gradlew test` (리포트: `build/reports/tests/test/index.html`)

---

## 1. 무엇을 검증하려 했는가

검증 대상을 네 가지로 나누고, 13개 구분·85개 QA 항목으로 정리해 모두 JUnit5 테스트와 연결했습니다. 테스트 이름(`@DisplayName`)에 QA ID를 넣어 리포트에서 바로 찾을 수 있게 했습니다.

| 분류 | 검증 내용 |
|---|---|
| **기본 단위·통합 테스트** | KST 시간 변환, 참여 조건 경계값, 외부 쿠폰 시스템 계약, 미션 조회·완료, 보상 지급·조회, API 규격, 비즈니스 시나리오 E2E |
| **동시성 제어와 성능 측정** | 반복·동시 요청에서 정책 유지, 비즈니스 키 중복 없음, 락 경합 시 처리 시간·건수 |
| **예외 상황 및 실패 케이스** | 쿠폰 시스템 통신 오류·타임아웃, 애플리케이션 예외, DB 장애, 요청값 검증 |
| **비즈니스 오류 상황** | 기간 외 참여, 전체 100회·일 10회·1시간 재참여 제한, 중복 보상, 쿠폰 한도 소진·발급 중지, 지급 가능 보상 없음 |

그 외 일자별 미션 조회 캐싱(QA-H)도 함께 검증했습니다.

## 2. 왜 해당 내용을 중요하게 판단했는가

- **성공 케이스는 확인이 쉽고, 코드가 확장되어도 쉽게 드러납니다.** 정상 흐름은 API를 한 번 호출해 보면 바로 확인되고, 이후 기능이 추가되어도 기본 시나리오 테스트(QA-A01)로 깨졌는지 금방 알 수 있습니다.
- **실패 케이스는 예상하지 못한 상황이고, 큰 손실로 이어질 수 있습니다.** 리워드 서비스는 포인트·쿠폰이라는 금전적 가치를 지급합니다. 한 번 잘못 지급된 보상은 되돌리기 어렵고, 반대로 지급이 누락되면 사용자 신뢰를 잃습니다.
  - 동시 요청으로 보상이 두 번 지급되거나, 미션 전체 100회 한도를 넘는 경우
  - 외부 쿠폰은 발급됐는데 DB 저장 전에 실패해 결과가 사라지거나, 재요청 시 쿠폰이 중복 발급되는 경우
  - 외부 시스템·DB 장애 시 데이터가 어중간한 상태로 남는 경우
- **그래서 장애·예외·실패·동시성 케이스를 중심으로 검증했습니다.** 경계값(시작 시각 포함, 종료 시각 제외, 99회/100회, 59분 59초/1시간, KST 자정)도 조건이 한 칸만 어긋나도 정책이 깨지기 때문에 초 단위로 확인했습니다.

## 3. 어떤 방법으로 검증했는가

JUnit5와 MockMvc로 가능한 경우를 모두 자동화했습니다.

| 방법 | 대상 |
|---|---|
| 단위 테스트 | Spring 없이 정책·시간 변환·쿠폰 재현체를 경계값 중심으로 검증 |
| 통합 테스트 | H2 In-memory DB와 실제 트랜잭션으로 서비스 흐름과 DB 제약조건 검증 |
| API 테스트 | MockMvc로 HTTP 상태 코드, 응답 포맷(`code`/`msg`/`data`), Content-Type, 요청값 검증 확인 |
| 장애 주입 | 쿠폰 클라이언트에 IO 오류·`SocketTimeoutException`·예상하지 못한 예외를 주입하고, DB 연결 실패를 재현 |
| 동시성 테스트 | `ExecutorService` + `CountDownLatch`로 요청을 동시에 출발시켜 결과 건수와 DB 상태 검증 |
| 성능 측정 | 동시 요청 수(10/50/100/200)별 처리 시간·성공·실패 건수를 `[PERF]` 로그로 출력하고, 건수와 정합성만 단언 |

## 4. 검증 결과는 무엇이었는가

QA 항목에 연결된 자동화 테스트가 모두 통과했습니다. 주요 결과는 다음과 같습니다.

### 기본 기능·비즈니스 규칙
- 기준 시각(2026-09-01 12:00 KST)에 기간 내 미션(0002, 0003)만 조회되고, 조회 → 완료 → 보상 요청 → 결과 확인 시나리오가 API로 끝까지 동작
- 참여 조건 경계값이 초 단위로 정확히 동작: 시작 시각 포함·종료 시각 제외, 전체 99회 가능/100회 불가, 당일 9회 가능/10회 불가, 59분 59초 불가/1시간 가능
- 1시간 재참여 제한은 자정을 넘겨도 유지되고, 일 10회 제한은 KST 자정에 초기화
- 포인트는 500회 샘플에서 5~10 전 범위가 나오고 범위를 벗어나지 않음
- 발급 중지·한도 소진 쿠폰은 후보에서 제외되고, 지급 가능한 보상이 없으면 `NO_REWARD`(200) 후 재요청 가능
- 미션 단위·참여 이력 단위 비관적 락으로 정책이 깨지지 않는 것을 확인했고, 인기 미션에서는 직렬 처리로 처리량이 제한될 수 있다는 점도 수치로 확인했습니다.

### 예외·장애
- 쿠폰 발급 IO 오류 → 503 `COUPON_COMMUNICATION_FAILED`, 보상 결과는 롤백되지 않고 `FAILED`로 저장
- 쿠폰 발급 타임아웃 → `FAILED` 저장, 쿠폰 시스템 회복 후 같은 이력번호로 재요청하면 **같은 리워드번호로 쿠폰 1개만 발급**
- 외부 발급은 성공했지만 저장 전에 실패한 경우 → 재요청 시 같은 쿠폰으로 복구, 중복 발급 없음
- 발급 시점에 한도가 소진되면 쿠폰을 제외하고 포인트로 재선정
- 애플리케이션 예외 → 500 `INTERNAL_SERVER_ERROR`, DB 연결 실패 → 503 `DATABASE_ERROR`, 두 경우 모두 참여 이력 생성 안 됨
- 필수값 누락 → 400 `MISSING_REQUIRED_VALUE`, 정의되지 않은 경로(404)·메서드(405)도 공통 응답 포맷 유지

## 5. 검증하지 못한 범위가 있는가

일반적으로 도출한 QA 케이스는 모두 확인했지만, 실제 운영에서는 테스트 환경에서 재현하기 어려운 이슈가 존재합니다.

| 범위 | 사유 |
|---|---|
| 여러 애플리케이션 인스턴스 + 공유 DB 환경의 동시성 | 단일 JVM, H2 In-memory에서만 검증 |
| 실제 HTTP 외부 쿠폰 시스템의 타임아웃·네트워크 오류 | 재현체에 예외를 주입하는 방식으로만 확인 |
| 대량 데이터에서의 목록 조회 성능 | 테스트 데이터 규모가 작음 |

이런 경우에 대비해 **운영에서 원인을 추적하고 복구할 수 있는 보완 작업**을 해 두었습니다.

- **요청 추적 로그**: 요청마다 traceId를 발급해 모든 로그와 응답 헤더(`X-Trace-Id`)에 남김 → 사용자 문의 시 해당 요청의 전체 흐름을 추적 가능
- **실패 상태 저장**: 쿠폰 통신 실패 시 보상 결과를 `FAILED`로 남기고 실패 사유를 기록 → 누락 없이 재처리 대상 파악 가능
- **멱등 재요청**: 같은 이력번호로 재요청하면 같은 리워드번호·requestId로 처리 → 재시도해도 중복 발급 없음
- **DB 유니크 제약**: 이력번호·리워드번호·참여 이력당 보상 1건을 DB 레벨에서 한 번 더 차단
- **prod 로그 파일 보관**: 일자별 롤링, 30일 보관
